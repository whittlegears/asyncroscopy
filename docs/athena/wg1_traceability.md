# ATHENA WG1 traceability: what this stack provides toward Infrastructure and Requirements

Sources: the WG1 slides ("WG1: Infrastructure and Requirements", Duscher and Crosby) and the TIBML "Instrument Control, Remote Operations and Data Streams" next-steps document. WG1 owns the services infrastructure (on-premises Kubernetes/OpenShift, token minting and verification, the user/admin portal with CILogon, the scheduler). This repository is the **instrument side** of that picture: the PyTango / Tiled / MCP servers that sit behind each instrument's endpoint proxy, the digital twin MCP servers, and the agentic workflows that call them. Each row says who owns the item and what evidence exists here. **All evidence is from the digital twin unless a row says otherwise.**

| WG1 item | Owner | What exists here | Evidence | Status |
| :-- | :-- | :-- | :-- | :-- |
| One framework that unifies automation of many instruments (no insular server-client interfaces) | WG1 / this repo | One Tango device layer and one MCP server for every instrument; YAML-described twins (XRD, Raman, AFM) get the same tools, job envelope, approval gate and trace as the STEM | `tests/test_yaml_sim.py`, `tests/yaml_sim_job_check.py`, `tests/yaml_sim_afm_check.py`, `docs/Adding_New_Hardware/new_instrument.md` | Implemented for twins; the STEM and any YAML instrument share one envelope. Generic map jobs across instruments: in progress. |
| Well-defined safety standards | WG1 (Crosby) / this repo | Risk policy per command; approval gate (auto/approve) with single-use grants; operator-only commands never on the agent endpoint; an agent endpoint must name its approval device; hardware stacks (`simulated: false`) start in approve and refuse auto; plan limits checked at reserve (stage, dose, duration); dry-run of any job | `tests/test_approval_mode.py`, `tests/test_configs_load.py`, `tests/test_dry_run_and_clock.py`, `docs/Operation/approval_mode.md`, `docs/Operation/dry_run.md` | Implemented. Hardware interlocks belong in the instrument's own PLC/vendor layer (the TIBML document's point), not in this software. |
| Safe access for remote users: endpoint proxy with TLS and token authentication | WG1 (token service, proxy blueprint, VPN) / this repo (the check at the MCP server) | Optional `mcp.auth`: every request needs a bearer JWT (signature from a public key or JWKS, expiry, issuer, audience); the token's subject is the caller in the trace and approval requests; scopes give roles (read / operate / approve) mapped onto the existing risk policy; a hardware endpoint bound beyond 127.0.0.1 without `auth` refuses to start. Agents send `ASYNCROSCOPY_MCP_TOKEN`. A development token minter stands in for WG1's service. Reference TLS proxy for the MCP and Tiled ports. Without `auth`, unchanged (self-reported `X-Asyncroscopy-Caller`) | `tests/test_endpoint_auth.py` (in-process HTTP: no/expired/wrong-issuer/wrong-audience/wrong-key tokens refused, read vs operate vs approve, subject recorded), `docs/Operation/remote_access.md`, `deploy/proxy/nginx.conf`, `startup_scripts/dev_tokens.py` | Implemented and tested with locally minted tokens only. Not yet run against WG1's token service (JWKS path untested end to end); the nginx config is unvalidated (no nginx here); the analysis server and Tiled do not verify tokens (Tiled keeps its service-to-service API key). |
| Digital Twin MCP Servers hosted in Kubernetes / OpenShift | WG1 hosts, this repo provides | The twin stack runs from one config with `run_servers.py` and `run_mcp.py`; a second isolated stack can run beside it. Deployment notes list each process's command, ports, settings, volumes, health check and startup order; the Tango database can bind an interface other than its client-facing name (`tango.bind_host`), DATA can advertise a Tiled service address (`ASYNCROSCOPY_TILED_PUBLIC_URI`), server output can go to stdout (`--log-to-stdout`), and the launchers exit non-zero when a server dies | [`docs/Operation/deployment_notes.md`](../Operation/deployment_notes.md), `docs/Adding_New_Hardware/second_stack.md`, `tests/test_run_servers.py`, `tests/test_process_manager.py` | Runs on Windows and Linux (fresh-clone checks). Ready to containerise; no container image or manifest exists yet, and none has been run. |
| Agentic agents / workflows and LLM servers | WG2 with WG1 | Agents speak to any OpenAI-compatible or `init_chat_model` provider (`ASYNCROSCOPY_MODEL_PROVIDER`, `OLLAMA_HOST`), so a locally hosted LLM server (vLLM, Ollama, LiteLLM gateway) plugs in by URL; agents send caller and run ids that an endpoint can authorise | `asyncroscopy/agents/__init__.py`, `docs/Operation/agents.md` | Implemented with local Ollama; not tested against a cluster-hosted LLM server. |

## Not claimed

- No authenticated identity from WG1's real token service yet: with `mcp.auth` the caller is a verified token subject, but only locally minted development tokens have been used. Without `mcp.auth` caller names are still self-reported.
- No container image or Kubernetes manifest exists, and none has been run; the deployment notes are checked against the code, not against a cluster. The multi-pod layout (Tango database reached through a Service name) is untested.
- No EPICS or Bluesky integration.
- No run of the new code on the Spectra 300.
